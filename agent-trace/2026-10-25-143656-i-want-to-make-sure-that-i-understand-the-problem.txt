● Yes to SQLite. LangGraph works too, but the shape of the data argues against
  using it the way you describe, with an agent working through each case on its
  own. I checked the dataset to ground this.

  What the data looks like

  - The evidence is small and shared: 94 files, 3.1 MB in total (24 SQL, 28
    JSON, 26 logs, 11 PNG screenshots, 4 PDFs, 1 TXT).
  - One file covers many people. evidence_03, a shift-handover text file, has
    status lines for dozens of accounts:
  2026-10-01T12:00:00Z | analytics_platform | analytics_2034 | ANALYTICS_PROFILE
  | IDENTIFIABLE | novak.tomasz@icloud.com
  - system_activity.csv has about 4,000 events: deletes, syncs, exports,
    data-flow checks, restore blocks and so on.

  So evaluating each case independently would re-read and re-interpret the same
  ~94 files 518 times. That costs a lot of tokens, it's slow, and two cases can
  read the same file differently.

  Recommendation: two stages

  Stage 1: ingest everything once into SQLite. This is where your DB idea pays
  off. Turn every evidence source into one common table of facts:

  observations(evidence_id, observed_at, system_id, resource_id,
               data_category, state, identifier, source_kind)

  - SQL snapshots: they're SQLite-compatible, so run them directly. Keep the
    replica name and snapshot time, because primary and replica copies can
    disagree.
  - Logs, JSON, TXT: parse them with code (regex or a JSON parser). No LLM
    needed.
  - PDFs and PNGs (15 files): extract with an LLM or vision model into a fixed
    schema, once. Cache the result by file hash.
  - Identities: combine user_identities and user_audit_log into an identifier →
    user_id alias table that includes past emails, phones and hashes. Normalize
    case, because the evidence has values like CHOI.JIHOON94@GMAIL.COM.

  Stage 2: per-case reasoning, mostly in plain code.
  1. Classify the request with an LLM. This is the one step that really needs
     it: multilingual text and subtle intent like export vs. erase. Batch it,
     cache it, and use a fixed output format.
  2. Resolve identity with a SQL lookup.
  3. Reconstruct state. For each resource linked to the user, take the latest
     observation at or before audit_at. SQL handles this well.
  4. Apply policy by mapping data_category to the action in deletion_rules.csv.
  5. Plan and serialize using the fixed ordering rules: phase, then operation
     order, then system_id, then resource_id.
  6. Validate against the output contract.

  This is deterministic, cheap, and easy to debug against the 32 samples. The
  LLM is used where its judgment adds value, not for joins and sorting.

  Where LangGraph fits

  The per-case flow is mostly a straight line with one early exit:

  classify ──NA──> END
     └─> resolve_identity → gather_observations → reconstruct_state
         → apply_policy → plan_steps → validate ──fail──> (repair / LLM review)
  ──┐
                                          └─pass──> END
   │

  ^───────────────────────────────────────┘

  LangGraph earns its place in two spots:
  - The validate → repair loop. An LLM steps in only when the deterministic
    result is ambiguous, for example an unlinked identifier, conflicting
    replicas, or an unclear "is this flow still active?"
  - Explaining the architecture in the AI interview. A graph diagram is easy to
    walk through.

  It isn't worth it if every node is an LLM call doing the investigation. That's
  the version I'd steer you away from.

  Suggested path: write the nodes as plain Python functions first and get them
  matching the samples. Wrapping them in a LangGraph StateGraph afterwards is
  cheap, so you can decide then whether the orchestration is worth it.

  Next step: profile the evidence formats (what fields each SQL table, JSON
  bundle and log type contains) and design the observations schema. Every later
  step depends on that table being right.

  Active connector repopulated downstream resource X.

  If something stays ambiguous after the deterministic pass, such as an
  identifier you can't link or two sources that disagree, add a fallback node

  The resulting graph:
  [ingest once]  parse structured files ─┐

● Starting from zero, I'd use a plain Python pipeline with no orchestration
  framework, SQLite as the store, and the Claude API called in only two places.

  Recommended stack

  Layer: Language
  Choice: Python 3.12 (you have 3.12.3), managed with uv
  Why: Best fit for the data work. code/main.py is already the expected entry
  point.
  ────────────────────────────────────────
  Layer: Orchestration
  Choice: Plain Python functions, one module per stage
  Why: The per-case flow is a straight line with one early exit, so a framework
  adds dependencies and indirection without buying much.
  ────────────────────────────────────────
  Layer: Storage
  Choice: stdlib sqlite3, no ORM
  Why: Built in. The SQL evidence snapshots can be loaded directly, and "latest
  state at or before audit_at" is one query.
  ────────────────────────────────────────
  Layer: Schemas and validation
  Choice: pydantic
  Why: One model each for observations, steps and output rows. It catches
  contract errors (bad operation/state pairs, numbering, phase order) before
  you submit.
  ────────────────────────────────────────
  Layer: PDFs
  Choice: pypdf first
  Why: If the 4 PDFs have a text layer, they need no model at all.
  ────────────────────────────────────────
  Layer: Screenshots, and PDFs without text
  Choice: Claude vision, one call per file, once
  Why: Use structured output into your observations schema. 15 files at most.
  ────────────────────────────────────────
  Layer: Request intent
  Choice: Claude, structured output {authorizes_deletion, language, reason}
  Why: Handles multilingual and subtle intent. Send the 518 requests through the

  Message Batches API, which costs 50% less.
  ────────────────────────────────────────
  Layer: LLM cache
  Choice: JSON on disk, keyed by sha256(input + prompt_version)
  Why: Reruns are free and give identical results, which the contract asks for.
  ────────────────────────────────────────
  Layer: Evaluation
  Choice: pytest plus an eval.py that scores against sample_output.csv
  Why: Measures status, step-level, field-level and sequence accuracy. Its
  output
  goes straight into evaluation_report.md.
  ────────────────────────────────────────
  Layer: Usage tracking
  Choice: Log response.usage from every call to a file
  Why: Generates usage_report.md automatically from the real final run.

  Model and cost

  - Model: claude-opus-5-5 at effort: "low", which suits classification and
    extraction.
  - Request classification: 518 requests × roughly 300 tokens ≈ 160K input
    tokens. At $4 per million input tokens that's under $1 before the batch
    discount.
  - Vision extraction: a one-time cost of well under $1.

  So the whole LLM bill is a few dollars at most, and it isn't worth optimizing
  until it works. If you want it even cheaper, claude-haiku-5-5 costs
  $0.10/$0.50 per million tokens, about 40× less. Only switch if it scores the
  same on the 32 samples; that's your call.

  Project layout

  code/
    main.py              # ingest (if cache is stale) → run all cases → write
  ../output.csv
    ingest/              # one parser per format: sql, json, log, txt, pdf,
  image(LLM)
    store.py             # SQLite schema + queries (aliases, observations,
  activity, rules)
    classify.py          # request intent (LLM, batched, cached)
    audit.py             # resolve identity → reconstruct state → apply policy
    plan.py              # findings / remediation / verification + ordering
    schema.py            # pydantic models + output validator
    llm.py               # Anthropic client, cache, usage logging
    eval.py              # scores against sample_output.csv
    evaluation/

  Where your earlier ideas fit: SQLite, yes, at the centre. LangGraph, only if
  you want the graph for the AI interview. Because each stage is a plain
  function, you can wrap them in a StateGraph later in about an hour without
  changing their logic.

  The design choice that matters most isn't the stack. It's the shape of the
  observations table and how well the parsers fill it. That's where I'd start
  next.

● It's closer than my last answer made it sound. The per-case logic is the same
  code either way, so the question is only what wraps it.

  Where LangGraph actually helps

  1. Diagram for the AI interview. graph.get_graph().draw_mermaid() gives you a
     picture of the architecture for free. You'll have to explain the design to
     an interviewer, and that helps.
  2. Branches and loops are visible. The NOT_APPLICABLE exit and a "validate →
     repair → validate" loop are declared as edges instead of buried in if/while
     code.
  3. One typed state object (CaseState) travels through the nodes. It's easy to
     see what each step reads and writes.
  4. Room to grow. If the samples show you need an LLM fallback for ambiguous
     cases, you add one node and one conditional edge.
  5. Tracing. With LangSmith (or another tracer) you can look inside any failing
     case node by node. That's useful when you debug the 32 samples.

  Where it costs you

  1. The two most important steps aren't per-case. Ingestion runs once over all
     94 files. Classification works best as one batch across all 518 cases
     (cheaper, and one cache). A graph where each run handles one case doesn't
     fit either step, so they end up outside the graph anyway.
  2. Most of its built-in features go unused. Checkpointing, resume,
     human-in-the-loop and streaming are built for long or interactive agent
     runs. Once the LLM results are cached, this job takes seconds.
  3. An extra layer when debugging. Stack traces go through the framework, and
     the rules for how state updates are merged can surprise you. Plain
     functions can be called directly from a test.
  4. Token tracking can get hidden. If you call the model through LangChain's
     chat-model wrappers, exact usage numbers for usage_report.md are harder to
     get. Calling the Anthropic SDK directly inside nodes avoids this.
  5. More dependencies to install. A small cost, but a real one for a "clean run
     from the README".

  Plain Python, honestly

  - Pros: fewest moving parts, quick to debug, each function testable on its
    own, batching across cases comes naturally.
  - Cons: no free diagram or tracing, you write your own retry loop, and the
    architecture story in the interview is less visual.

  My verdict

  If you know LangGraph and value the interview story, use it. Just set it up
  this way:

  main.py
    ├─ ingest()                      # global, once, outside the graph
    ├─ classify_all(cases)           # global, batched LLM, outside the graph
    └─ for case in cases:
          case_graph.invoke(state)   # LangGraph: resolve → reconstruct → policy
  → plan → validate ⟲ repair

  - Keep the nodes deterministic, as you planned.
  - Call the Anthropic SDK directly in the few nodes that need a model.
  - Don't try to force ingestion or batch classification into the graph.

  That way you get LangGraph's benefits without its drawbacks. If you don't care
  about LangGraph, plain functions are a bit simpler. Either choice is fine;
  what matters for the score is the ingestion quality and getting the rules
  right, not the orchestration.

● Partly. Being vendor agnostic is a good requirement, and it does tip the
  balance toward your stack. But one distinction matters for how you'll explain
  the design in the interview.

  Being vendor agnostic comes from LangChain, not LangGraph

  LangGraph only runs the graph. A node can call any SDK, or no model at all, so
  the graph itself is neutral either way. The ability to swap providers comes
  from LangChain's chat-model layer (langchain-core), which pairs naturally with
  LangGraph:

  from langchain.chat_models import init_chat_model

  llm = init_chat_model(os.environ["LLM_MODEL"])   # e.g.
  "anthropic:claude-opus-5-5", "openai:...", "google_genai:..."
  classifier = llm.with_structured_output(RequestIntent)   # pydantic schema,
  same code for every provider

  Changing the provider is then just changing an environment variable. This also
  fixes two concerns I raised earlier:
  - Token usage: every response carries a standard usage_metadata field (input
    and output tokens) for every provider, so usage_report.md is still easy to
    generate.
  - Images: LangChain has a standard image content block, so the screenshot
    extraction is provider-neutral too.

  Other ways to stay vendor agnostic

  - LiteLLM: one completion() call for 100+ providers. Lighter, but it doesn't
    integrate with LangGraph.
  - Your own adapter: a ~40-line LLMClient interface with one class per
    provider. Fewest dependencies, but you maintain it.

  With LangGraph already in the picture, LangChain's model layer is the natural
  choice.

  Trade-offs

  - No provider-specific batch discounts: the Batch API's 50% saving is lost.
    That doesn't matter here: the total bill is a few dollars, and caching makes
    reruns free.
  - Structured output quality varies by provider. If you claim the system is
    vendor agnostic, run the 32 samples on at least two providers and record the
    results in evaluation_report.md. That turns the claim into evidence.
  - Cache keys must include the model name, so switching providers doesn't serve
    stale answers.
  - Pin your versions. LangChain packages change quickly, and a clean run from
    the README has to work.

  Updated recommendation

  Use LangGraph + LangChain chat models:
  - Ingestion and batch classification run outside the graph.
  - The per-case graph uses deterministic nodes.
  - The provider and model are chosen through LLM_MODEL, with API keys from
    .env.
  - Every LLM call goes through one small wrapper that adds caching and usage
    logging.

  With your requirements stated (vendor agnostic, a clear architecture story),
  this is the better fit than my plain-Python version.

  Next step: profile the evidence formats and design the observations schema,
  since every node after ingestion reads from it.

● The idea is simple. The hard part is being exact. Every step is graded field
  by field, so getting a case "roughly right" still scores poorly. Here's what I
  found when I probed the data.

  1. The samples are easier than the real set

  - Historical emails: only 3 of 32 sample requests use an old email address,
    but 100 of 518 evaluation requests do. Something that passes the samples
    using current emails alone will fail on about a fifth of the real set.
  - Sample case_11 is the friendly kind. One handover file, captured at exactly
    audit_at, lists every resource with the user's email:
  integration_service | data_flow_9522 | DATA_FLOW         | ACTIVE   |
  novak.tomasz@icloud.com
  security_service    | audit_record_9394 | SECURITY_AUDIT_LOG | FOUND | user_32
    Other cases spread the evidence across SQL replicas, screenshots and logs,
    with no single summary file.

  2. Linking evidence to a person

  Nothing in evidence_files.csv says which case a file belongs to. A record can
  point to the user in several ways:
  - a current or past email, sometimes in different capitalisation
    (CHOI.JIHOON94@GMAIL.COM);
  - the user_id (as in the audit record above);
  - a phone number, current or past;
  - an email_hash: I confirmed it's the SHA-256 of the raw email, so you must
    hash every past email too;
  - a resource ID connected through LINK_RESOURCE_IDENTITY events in the
    activity log.

  On top of that, decoy records for other people sit in the same files. Miss a
  link and a finding disappears; make a wrong one and you report someone else's
  data.

  3. Rebuilding the state at a point in time

  - The same resource shows up in many sources at different times. You need the
    latest state at or before audit_at, and the boundary is inclusive: case_11
    cites a file captured at exactly audit_at. Evidence captured after audit_at
    must be ignored even though it's in the dataset.
  - Deleted data can come back. The activity log contains "Active connector
    repopulated downstream resource X" 31 times, plus one restore job that
    brought data back. A record deleted on Monday can be present again on
    Tuesday.
  - Replicas can disagree. The primary database may show a record deleted while
    a failover or regional replica still has it. Case_05 is reported COMPLETE,
    but a failover replica snapshot proves the account still exists.

  4. Claims vs. evidence

  reported_status is wrong in both directions, and reported_result=SUCCESS in
  the activity log is only a claim too. You decide what counts as proof and
  which source wins when sources conflict.

  5. Rule conditions need judgment

  Several rules depend on a condition, so the rules file isn't a simple lookup
  table:
  - Support messages are redacted (not deleted) only if the conversation
    contains context that must be kept.
  - Support attachments are deleted only if they belong solely to the subject.
  - Legal-hold records are kept only if the hold is still active, which probably
    needs the legal retention register PDF.
  - Security audit logs are kept only within the retention period.
  - Backups are kept, but restores must be blocked.
  - Tombstones keep the user_id but lose the name, email, phone and hash.

  Deleting too much is as wrong as deleting too little. Records that must be
  retained get VERIFY_RECORD_PRESENT, not deletion.

  6. Matching the expected answer exactly

  - What goes into verification: in case_11, the expected answer verifies the
    account and the audit record even though neither had a finding. Verification
    covers the whole required end state.
  - Which evidence to cite: in case_11, activity_3817 also shows the data flow
    as enabled, but the expected answer cites the handover file evidence_03.
    When several sources prove the same fact, you have to learn from the samples
    which one to cite.
  - Ordering: phase, then operation order, then system_id, then resource_id. One
    missing or extra step shifts every later step number and hurts sequence
    accuracy.

  7. Reading screenshots and PDFs exactly

  Extracting from screenshots and PDFs has to get IDs character-perfect. Reading
  analytics_2034 as analytics_2084 silently breaks a finding.

  Where the effort should go

  The graph, the SQLite store and the LLM classifier are about 20% of the work.
  The other 80% is identity linking, point-in-time state reconstruction, the
  edge cases in the rules, and the citation conventions. That's why I keep
  pushing the observations schema and the per-format parsers as the first thing
  to build.

● No, not per case. Every file gets read once, at the start, and turned into
  rows in a database. After that, step 4 for any case is a quick lookup. The
  effort is still real, but it moves from per-case searching into the one-time
  reading step.

  Read once, look up many times

  Without ingestion: for each of the 518 cases, open up to 94 files and search
  them. That's about 48,000 file reads, with the same images and PDFs
  interpreted again and again.

  With ingestion:
  1. Once: open each of the 94 files, pull out every record, and save it as a
     row in one SQLite table.
  2. Per case: run one query, find rows where identifier is one of [user_05,
     leila.haddad@yahoo.com, +212…, 62667ed0…].

  The whole evidence folder is only 3.1 MB, so the table is small and the query
  is instant.

● Part 1: What audit_at is

  Think of audit_at as the moment the auditor takes a photo of all the systems.
  Each case asks one thing: was this person's data really gone at that moment?

  The dataset isn't a single moment. It covers almost a whole year, from
  evidence captured 2026-01-29 to 2026-10-01, and all 518 cases share the same
  files. Each case has its own photo moment, so for any given case some evidence
  comes from its "future".

  Why we care

  1. The expected answer is fixed to that moment. The grader's answer is "what
     was true at audit_at". If someone fixed the leak a week later, the answer
     is still INCOMPLETE, because at the photo moment the data was still there.
  2. Things change over time. Data gets deleted, synced back and restored.
     Looking at the wrong moment gives the wrong answer.
  3. You can't cite the future. A finding or verification must cite evidence
     that existed at audit_at. Citing a file captured afterwards is wrong by the
     contract.

  The rule: for each case, use only evidence captured, and activity that
  happened, at or before audit_at. Ignore everything after it, as if it doesn't
  exist.

  ---

  Part 2: "Deciding which mention wins"

  One record usually shows up in several places: activity-log rows, a database
  snapshot, a JSON export, a screenshot. They often disagree. You need fixed
  rules for which one to believe.

  The five rules

  Apply them in this order for each record:

  Rule 1: Drop everything after audit_at.

  ▎ In case_24, evidence_02 (09-17) is dropped. In case_01, evidence_03 and
  ▎ evidence_04 were dropped too.

  Activity rows (reported_result = SUCCESS) and reported_status say what a

  exists. When they disagree, the evidence wins.

  ▎ In case_24, three SUCCESS claims lose to one export showing the account
  ▎ still there.

  Rule 3: The latest evidence wins.

  it's gone, as long as August is still before audit_at.

● One question tells them apart:

  ▎ Is this someone saying an action happened, or someone looking and seeing
  ▎ what's there?

  - Claim: a report that an action was done or succeeded. "I deleted it." "Sync
    finished." "Status: COMPLETE."
  - Evidence: an observation of what exists, or doesn't, at a specific time. "I
    queried the table at 23:00 and this row is there." "Lookup returned 404."

  A claim can be wrong, because the process may have failed silently. Evidence
  shows the actual state.

  ---

  Claims (never trust these on their own)

  Where: reported_status in the request
  Example from the data: COMPLETE, PARTIALLY_COMPLETE, NOT_STARTED
  ────────────────────────────────────────
  Where: reported_result on action rows in system_activity.csv
  Example from the data: DELETE_RECORD … account_5334 … SUCCESS
  ────────────────────────────────────────
  Where: Action wording in activity rows
  Example from the data: "Deletion worker submitted primary profile…",
  "…reported
  the requested operation as completed", "Replication worker reported its final
   checkpoint", "Policy action completed for X"
  ────────────────────────────────────────
  Where: Status labels inside records
  Example from the data: "account_status": "DELETED" (see the tombstone trap
  below)
  ────────────────────────────────────────
  Where: Classification activity
  Example from the data: "Privacy intake classified request for X as
  non-deletion": still read the request text yourself

  The trap: a claim inside an evidence file

  From customer_data_snapshot_bundle_20260915.json:

  { "resource_id": "tombstone_440",  "subject_reference": "user_541",
    "name": null, "email": null, "phone": null, "email_hash": null,
    "account_status": "DELETED" }                          ← label and fields
  agree ✅

  { "resource_id": "tombstone_9178", "subject_reference": "user_542",
    "name": "Kofi Addo", "email": "addo.kofi@gmail.com",
    "phone": "+233 24 991 1328", "email_hash": "4f4b9c98…",
    "account_status": "DELETED" }                          ← label says deleted,
  fields say otherwise ❌

  Both say DELETED. But tombstone_9178 still holds the name, email, phone and
  hash. The ACCOUNT_TOMBSTONE rule allows only the stable user_id. The status
  label is a claim; the field values are the evidence. So this record gets
  REPORT_EXPOSED_PII, not "compliant".

  Rule: trust the fields, not the labels.

  The grey zone: the activity log isn't all claims

  system_activity.csv mixes three kinds of rows:

  Kind: Action claims
  Examples: DELETE / REDACT / ANONYMIZE / SYNC with SUCCESS, "final checkpoint",

  "policy action completed"
  How to use it: Never proof. Only tells you which resource to check.
  ────────────────────────────────────────
  Kind: Checks (observations)
  Examples: "Connector status check confirmed that data flow X remains enabled",

  "Restore-access check confirmed that archive X can still be restored",
  "Active connector repopulated downstream resource X"
  How to use it: Evidence of an active flow or restore risk. Can be cited by
  activity_id.
  ────────────────────────────────────────
  Kind: Routine events (leads)
  Examples: index refresh, email sent, export created, cache refresh,
  LINK_RESOURCE_IDENTITY
  How to use it: Not proof of state. They tell you where copies may exist
  (search
  index, export, email log) or which resource belongs to which user. Follow
  them up in the evidence files.

  Two more sources can be cited:
  - user_audit_log.csv rows (audit_id) are evidence about identity history, for
    example proving an old email belonged to this user.
  - activity_id for check rows like the ones above.

  One caveat: all 32 samples cite only evidence files, never an activity_id.
  Even in case_11, where activity_3817 also showed the flow enabled, the
  expected answer cites evidence_03. So the working rule is: when a file and an
  activity row prove the same thing, cite the file. Use an activity or audit row
  only when no file covers it. We should check this against more samples when
  we build the citation logic.

  ---

  How this goes into the code

  During ingestion, tag every row in the observations table with a kind:

  kind = 'evidence' | 'check' | 'claim' | 'lead'

  - Deciding a record's state (step 5) uses only evidence, plus check for flows
    and restores.
  - Finding records (step 4) uses everything, including claim and lead rows,
    because they point you to where to look.
  - Citations prefer evidence files, then check rows.
