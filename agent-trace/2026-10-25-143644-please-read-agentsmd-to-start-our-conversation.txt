  What the data looks like (and why it matters)

  Format: SQL (24)
  Shape: Typed tables (customer_profiles, support_records…) plus generic
  customer_data_primary / _read_replica / _eu_west… tables that store the
  record as record_json. There's also a snapshot_scope table.
  What it means for the schema: Each row needs a copy label (primary or
  replica).
  A snapshot lists a whole table, so a missing row proves the record was
  absent.
  ────────────────────────────────────────
  Format: JSON (28)
  Shape: 4 shapes: snapshot bundles, service exports, list-style ledgers
  (result:
  FOUND/NOT_FOUND), and single collections
  What it means for the schema: One loader per shape. The time comes from the
  record's own timestamp field if it has one.
  ────────────────────────────────────────
  Format: Logs (26)
  Shape: About 7 line formats: key=value, pipe-separated, JSON, syslog,
  bracketed
  and cloud runtime. The lookup_key=<email> sits on the started line and
  resource_id sits on the completed line.
  What it means for the schema: Lines need to be joined by trace_id to connect
  an
  identifier to a resource.
  ────────────────────────────────────────
  Format: Text (1)
  Shape: Pipe-separated handover lines
  What it means for the schema: Simple parser
  ────────────────────────────────────────
  Format: Activity
  Shape: LINK_RESOURCE_IDENTITY rows link a resource directly to an email and
  user_id. The other rows are claims.
  What it means for the schema: Pull identifiers out of the details text

  The same identifier shows up under many field names: email, requester_email,
  owner_email, customer_email, subject_selector, lookup_key, match_key,
  correlation_key, subject_reference, and inside free text in support messages.
  Some are written in capitals (OBI.ADAEZE@ICLOUD.COM). Everything therefore
  gets normalized into one canonical form.

  The database is written to code/.cache/audit.db and rebuilt from scratch on
  every run. That should take a few seconds and keeps runs deterministic. The
  cached AI results live separately, so a rebuild doesn't make new AI calls.

  Proposed schema (three layers)

  -- 1. Raw tables: CSVs loaded unchanged
  requests(case_id PK, split /*eval|sample*/, email, requested_at,
  reported_status,
           reported_at, audit_at, request_text)
  identities(user_id PK, name, email, phone, email_hash, updated_at)
  identity_audit(audit_id PK, user_id, event_time, field_name, old_value,
  new_value)
  activity(activity_id PK, event_time, event_type, source_system, target_system,
           resource_id, reported_result, details)
  rules(rule_id PK, data_category, condition, required_action)
  evidence_files(file_id PK, file_path, origin, captured_at)

  -- 2. Identity index: every identifier a user ever had, normalized
  identifiers(user_id, kind /*email|phone|email_hash|name|user_id*/, value,
  raw_value,
              source /*'current' or audit_id*/, valid_from, valid_to)
    INDEX (kind, value)

  -- 3. Evidence: one row per "source X saw resource R at time T"
  observations(
    obs_id PK, evidence_id /*file_id|activity_id|audit_id*/, evidence_kind
  /*file|activity|audit*/,
    locator /*table, line no., JSON path — for debugging*/,
    observed_at, system_id, resource_id, store /*e.g.
  customer_data_read_replica*/,
    copy_role /*primary|replica|export|log…*/, record_type /*USER_PROFILE… if
  stated*/,
    state /*PRESENT|ABSENT|NULL for a pure claim*/,
    name, email, phone, email_hash, user_ref,   -- identifier fields as exposed
    attrs_json /*enabled, restore_allowed, retention_until, account_status,
  message_text…*/
  )
  obs_identifiers(obs_id, kind, value)   -- every identifier found in the
  observation, incl. free text
    INDEX (kind, value)
  coverage(evidence_id, observed_at, system_id, store, copy_role)
    -- "this source lists EVERY record of store at T" → lets us prove absence

  How a case uses this: the request email is looked up in identifiers to get the
  user_id and all of that user's identifiers. Those identifiers are matched in
  obs_identifiers, which gives the resource_ids. Then all observations and
  coverage rows for those resources up to audit_at are collected. Steps 1–4 of
  the recipe we walked through become SQL queries, and only step 5 (working out
  each record's state) needs real logic.

  Activity rows also go into observations. Pure claims get state = NULL, so they
  can point to a resource but never prove its state. The check rows we called
  evidence yesterday (CHECK_DATA_FLOW, CHECK_RESTORE_ACCESS) do get a state.
